    教程写作 SOP¶

    适用范围¶

    这份 SOP 用于规范整个 tutorial/ 下的正式讲义写作方式，目标是把已经验证有效的写法固化下来，减少后续每次写课时重新决定结构、语气、代码组织方式的成本。

    当前默认以这一份正文作为基线样本：

    • Week 1 课程 01 正文

    这份 SOP 主要约束两类文档：

    • 正式讲义正文
    • 配套代码页

    它不要求立刻回改所有旧文档，但后续新增正式讲义默认都应遵守。

    写前¶

    1. 先确认课程定位¶

    动笔前先回答清楚：

    • 这节课在整个阶段中的作用是什么
    • 读者的前置知识是什么
    • 这节课解决哪些问题，不解决哪些问题
    • 这节课是偏“方法论”、偏“结构原理”，还是偏“模板与题型”

    如果这四点还不清楚，不要直接开始堆内容。

    2. 先确认路径¶

    正式讲义统一使用以下目录结构：

    • 正文：notes/<stage>/weekX/lessonY/content.md
    • 配套代码页：notes/<stage>/weekX/lessonY/code/*.md

    默认示例：

    • notes/intro/week1/lesson1/content.md
    • notes/intro/week1/lesson1/code/language-conversion.md

    3. 先确认原课映射与出处¶

    如果课程依赖原课源码、实验程序、演示代码或外部题目，动笔前必须先整理出处。

    正文中允许写的出处类型只有三类：

    • 题目出处
    • 课程实验程序
    • 课程演示程序

    正文不再把 Java 源码路径作为主要阅读入口。

    4. 先确认本课是否需要完整代码页¶

    判断规则：

    • 如果只是为了讲一个局部逻辑，正文放必要代码片段即可
    • 如果读者需要看到完整可读版本，必须单独开代码页
    • 完整代码默认不直接堆在正文里

    写中¶

    1. 正文固定顺序¶

    正式讲义默认按以下顺序组织：

    1. 课程定位
    2. 学习目标
    3. 原课映射
    4. 核心知识讲解
    5. 习题
    6. 每日 CF
    7. 复盘要点
    8. 完成标准

    如果课程确实不需要某一节，可以省略；但不要随意打乱主顺序。

    2. 讲解展开顺序¶

    解释性内容优先采用这个顺序：

    1. 先给直觉
    2. 再给形式化表达
    3. 最后给例子

    适用场景包括：

    • 复杂度
    • 数据结构行为
    • 算法性质
    • 数学结论

    不要一上来就堆公式，也不要只停留在口语化类比而不落到严格定义。

    3. 每个抽象点尽量跟短例子¶

    默认规则：

    • 一个抽象步骤后尽量跟一个短例子
    • 例子优先选当前课程或紧邻课程会遇到的基础题型
    • 例子不要提前引入后续专题

    如果例子只是解释辅助，可以用引用块承接：

    > 例子：
>
> - ...
> - ...

    4. 配合代码讲解时怎么写¶

    硬规则：

    • 正文只放必要的 C++ 片段
    • 正文里的代码片段必须服务于讲解，不是为了把整份代码抄一遍
    • 如果需要完整代码，跳转到 code/*.md

    推荐顺序：

    1. 先贴必要片段
    2. 再解释这段代码为什么这样写
    3. 最后给出“完整代码见代码页”的入口

    5. 数学与代码标记规则¶

    这是硬规则。

    数学对象统一使用数学公式语法¶

    规则如下：

    • 行内数学公式使用 $...$
    • 独立成行的块级数学公式使用 $$...$$

    包括但不限于：

    • 变量：\(n\)、\(m\)、\(q\)、\(i\)
    • 复杂度：\(O(n)\)、\(O(n \log n)\)、\(O(1)\)
    • 范围与不等式：\(n \le 10^5\)、\(2^k < n \le 2^{k+1}\)
    • 求和、期望、集合符号：\(\sum n\)、\(\mathbb{E}\)、\(\mathcal{I}_n\)

    不要把这类对象写成反引号代码样式。

    真正的代码标识符继续用反引号¶

    包括但不限于：

    • push_back
    • solve()
    • vector<int>
    • long long
    • unordered_map

    不要把真正的代码标识符改写成数学公式。

    一句话总结：

    • 数学对象用 $...$
    • 代码对象用反引号

    6. 代码页目录规则¶

    这是硬规则。

    • 完整代码统一放在 notes/<stage>/weekX/lessonY/code/*.md
    • 正文和课程概览都链接到代码页 .md
    • 不直链原始源码文件
    • 不用浏览器直开源码文件作为主要阅读入口

    代码页命名要求：

    • 文件名使用稳定英文名，如 complexity.md
    • 页面标题使用可读中文或中英混合标题，如 Complexity C++ 译写

    7. 链接与出处规则¶

    正文中涉及来源时，必须写清楚来源性质。

    允许的表达：

    • 题目出处：LeetCode 912. Sort an Array
    • 程序性质：课程实验程序
    • 程序性质：课程演示程序

    不推荐的表达：

    • 只给文件名，不说出处
    • 只给 Java 路径，不给读者可直接阅读的 C++ 页面

    8. 练习与每日 CF 组织规则¶

    默认规则：

    • 主线练习和每日 CF 分开写
    • 不把每日 CF 混进主线习题
    • 每日 CF 要写清题目、定位、建议限时、复盘点

    入门阶段额外规则：

    • 主线不额外铺外部 OJ 题
    • 练习优先用课内整理、复杂度判断、模板默写、局部推导

    写后¶

    1. 自查结构¶

    检查正文是否满足：

    • 是否先讲课程定位，再讲学习目标，再讲原课映射
    • 是否保持主顺序清晰
    • 是否把抽象内容写成“直觉 -> 形式化 -> 例子”

    2. 自查表达¶

    检查正文是否满足：

    • 数学对象是否统一用 $...$
    • 代码标识符是否仍然用反引号
    • 是否存在口语化说明过多、但没有落到严格表达的段落
    • 是否存在公式直接出现、但前面没有铺直觉的段落

    3. 自查代码组织¶

    检查正文是否满足：

    • 正文里是否只保留必要代码片段
    • 完整代码是否已放入 code/*.md
    • 代码页标题、出处、正文链接是否完整
    • 是否还存在源码直链入口

    4. 自查链接¶

    检查课程正文与课程概览：

    • 两边配套代码入口是否一致
    • 代码页链接是否能打开
    • 返回链接是否正确

    5. 构建检查¶

    写完后必须至少执行一次：

    uv run mkdocs build

    确认无坏链、无路径错误、无明显渲染异常。

    禁忌清单¶

    以下写法默认禁止：

    • 在正文中保留 Java 路径作为主要阅读入口
    • 把整份完整源码直接堆在课程正文中
    • 把数学对象写成反引号代码样式
    • 把代码标识符写成数学公式
    • 在正文里保留“为什么不选另外两题”这类低价值旁支说明
    • 用浏览器直开源码文件作为主要阅读入口
    • 没写出处就直接挂代码页链接
    • 练习和每日 CF 混在一起写

- 目标 3

### 小节标题

> - 例子 1
